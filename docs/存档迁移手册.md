# 存档迁移手册

这份手册规定小镇版本更新时如何保证旧存档可以继续游戏。存档兼容不是发布后的补救工作，而是改变存档引用含义时必须随改动完成的检查项。

## 强制规则

- 只要修改了存档中会引用的活动、活动位置、道具名称、位置锚点、角色、效果、任务状态或任何模块的存档字段，就必须同时检查旧存档迁移。
- `sourceFingerprint` 只能发现编译数据发生过变化，不能自动把旧活动、旧道具或旧锚点转换成新定义。需要转换的字段必须登记明确的历史迁移规则。
- 已经随版本发布的迁移规则不能删除。跳过多个版本读取存档时，迁移要能够按旧指纹逐段执行到当前版本。
- 迁移必须在当前编译数据的严格校验之前执行，并且可以重复执行。迁移后的存档要使用当前指纹重新保存。
- 不能对整个存档做没有上下文的全局文字替换。同一个道具名称可能仍被其他活动或历史任务合法引用，规则必须同时限定活动 ID、位置 ID、目标类型和动作。

## 标准流程

1. 在修改活动或世界数据前，保存修改前生成的 `town_world.json` 中对应 `activityIntegrationReceipt.sourceFingerprint`；修改后重新生成并记录新的指纹。
2. 在 `game/world/presentation/session/TownSaveSchemaRegistry.gd` 登记迁移 ID、旧指纹、新指纹和精确字段规则。规则需要说明旧值、新值以及最小匹配范围。
3. 在对应模块的 `prepare_restore` 入口调用统一迁移表，然后再执行当前定义的字段、占用关系、效果和幂等性校验。
4. 为每条迁移至少补一条旧存档回归测试，覆盖本次实际受影响的状态。若改动涉及进行中的执行、reservation、未完成任务或已结算效果，要分别覆盖这些状态。
5. 验证“旧存档读取成功 → 按当前定义继续 → 再保存”的闭环，并检查重新保存后的存档只包含当前引用，不再保留旧值。
6. 在同一批次更新 `更新日志.md`，说明玩家可见的旧存档兼容修复；打包时把更新日志放进玩家收到的压缩包。

## 当前已登记迁移

### 2026-08-10 公共食堂活动目标和服务容量调整

提交 `543c40b` 调整了公共食堂的递餐和准备面团目标位置，并把公共食堂服务容量从 2 调整为 4。旧版已完成或进行中的活动执行仍然记录 `公共食堂备餐柜`，当前活动定义分别使用 `公共食堂递餐口` 和 `公共食堂面团操作台`；旧版地点服务状态仍记录容量 2。迁移只对以下明确字段进行升级：

- 活动：`activity_baker_prepare_dough`
- 位置：`slot_baker_prepare_dough_01`
- 目标类型：`prop`
- 动作：`准备面团`
- 旧目标：`公共食堂备餐柜`
- 新目标：`公共食堂面团操作台`
- 活动：`activity_dining_serve_meal`
- 位置：`slot_dining_serve_meal_01`
- 目标类型：`prop`
- 动作：`取餐`
- 旧目标：`公共食堂备餐柜`
- 新目标：`公共食堂递餐口`
- `placeServiceStates.公共食堂.service_capacity`：`2` → `4`

对应迁移 ID 为 `2026-08-10-public-dining-prepare-dough-target`，实现和历史指纹登记在 `TownSaveSchemaRegistry.gd`。食堂取餐活动仍然合法使用 `公共食堂备餐柜`，因此不能把这个名称从整个存档中批量替换。

## 发布前检查项

每次涉及存档引用的版本更新，都要完成以下检查：

- [ ] 找到修改前、修改后的源指纹，并确认迁移链可以从已支持的历史版本走到当前版本。
- [ ] 迁移规则只匹配明确的业务身份，不依赖显示名称的模糊搜索。
- [ ] 旧存档恢复测试通过，且测试包含至少一个真实受影响的历史字段。
- [ ] 旧存档恢复后重新保存，检查当前指纹和当前引用已经落盘。
- [ ] 运行 `tools/guards/run_guards.sh`。
- [ ] 运行与改动范围匹配的 Godot 无头测试，并确认测试后源码目录没有意外变化。
- [ ] 更新根目录 `更新日志.md`，打包时复制到最终压缩包。
